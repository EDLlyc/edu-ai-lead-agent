# 修复 Agent vs 整篇重写（2026-09-30）

## 问题

文案被规则或审查拦下后，线上的修复是把问题清单和旧稿交给生成模型，整篇重写一次。
这次做了一个会调用工具的修复 Agent：只改被标出的地方，事实和品牌句只能原样取自证据和品牌资料。
要回答的是：它能不能比整篇重写修得更好，或者更省。

## 一套工具，三处使用

`app/application/services/copy_repair_tools.py` 里的 `build_repair_tool_registry(workspace)` 定义了
5 个工具（check_draft、find_evidence、replace_claim、drop_claim、rewrite_hook），名字、说明、
入参出参 schema、超时、大小上限和拒绝码只写一次：

| 用在哪 | 怎么接 |
|---|---|
| 修复 Agent | `copy_repair_agent.py` 把 `registry.model_tool_schemas()` 交给智谱函数调用，逐个执行模型发起的调用 |
| 本地运维 | `app/copy_repair_mcp_main.py` 用同一个注册表起 stdio MCP 服务，服务说明和 Agent 系统提示共用 `REPAIR_TOOL_RULES` |
| 评测 | `evals/copy_repair/runner.py` 让 Agent 通过同一个注册表修复埋雷稿，再过线上同样的规则和审查 |

工具失败时，函数调用和 MCP 返回同一种结构化错误：`error_code`、`retryable`、`hint`，参数错误时还有 `fields`。

## 方法

- 选题：生产上真实通过的选题。先生成一稿，规则和审查都通过的才用。
- 埋雷：`evals/copy_quality/mutations.py` 的已知缺陷，只保留被规则或审查拦下的埋雷稿。
- 每份被拦稿从同一个起点修两次：修复 Agent；线上的整篇重写（draft_version=2，带问题清单和旧稿）。
- 修好 = 修复稿再过规则和审查（v22 审查）都不拦。缺陷去掉 = 埋入的句子或 claim 不在修复稿里。
- 一次性生产容器、只读数据库、有调用上限。每版单次运行，样本小；审查是模型判断，不是人工标注。

## 结果

| 版本 | 被拦稿 | Agent 修好 | 整篇重写 修好 | 先 Agent 后重写 修好 | Agent 每次修复输入 token | 重写 每次修复输入 token |
|---|---|---|---|---|---|---|
| v1（生成 v27） | 32 | 10（31%） | 27（84%） | — | 7,386 | 7,180 |
| v2（生成 v28） | 20 | 13（65%） | 18（90%） | 19（95%） | 8,247 | 5,513 |
| v3（生成 v28） | 28 | 25（89%） | 25（89%） | 28（100%） | 5,383 | 6,084 |

v1、v2 用同样 3 条选题，v3 多用 1 条。每次运行都重新生成初稿和埋雷稿，所以版本之间不是严格配对；同一次运行里两种修复是配对的。

### 每一版改了什么

- **v1 → v2。** v1 有 20/32 次用完 4 轮，常常是已经改好了引导语，又去改没被标出的 claim；15 次改写因为转述证据或品牌句被工具拒绝。
  v2 做了四件事：
  - 只允许改被标出的 claim；问题没点名 claim 时，只能改引导语。
  - 拒绝时返回最接近的原文候选句。
  - check_draft 通过且被标出的地方都改过时，循环自动结束。
  - 轮数上限从 4 提到 6。
- **v2 → v3。** v2 失败的多是重写的引导语本身违反规则，比如写进了数字，Agent 转去找证据。
  v3 让 rewrite_hook 在应用前先跑引导语规则，不合规就不应用，并说明原因。

## 结论

- v3 的修复 Agent 和整篇重写修好率持平，都是 25/28。Agent 每次修复的输入 token 少约 12%，但平均要 2.8 次模型调用，耗时更长。
- 两者修不好的稿子不重合。先用 Agent、没修好再整篇重写，28/28 全部修好，每次修复输入约为整篇重写的 1.4 倍。
- Agent 的改动是局部的：没被标出的内容不会变，事实和品牌句都是证据或品牌资料的原文，每一步都有工具调用记录。
- 剩下的失败多是审查随后又指出品牌说法无依据。整篇重写也出现了同样的情况。
- 样本小：每版单次运行，被拦稿集中在引导语缺陷，事实类缺陷在 v3 只有 1 份被拦下。
  现在还不能说 Agent 更好，线上仍用整篇重写。要上线“先 Agent 后重写”，需要更多选题、多次运行，并加一个默认关闭的开关。

## MCP 侧的验证

- `tests/contract/test_copy_repair_mcp.py` 检查三件事：
  - MCP 列出的工具和函数调用的 schema 逐字一致。
  - 服务说明包含 Agent 的同一段规则。
  - 编辑只改进程内的工作稿，拒绝和参数错误都是结构化结果；stdio 进程离线可用，日志只写 stderr。
- `--copy-run-id` 的读取路径在生产库上只读试过：最近 5 条文案任务都能加载，check_draft 和 find_evidence 正常。
  本机开发库的数据停在 8 月，引用的品牌片段已经重新导入过，所以本机加载会明确报错，不会静默出错。
