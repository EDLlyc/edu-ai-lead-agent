# 公众号周一自动调度生产部署

## Goal

让生产服务器从 `2026-09-07` 起，在每周一上海时间 09:00 自动创建一次真实的公众号周内容任务，使用既有业务数据和质量门禁生成三篇相互独立的文章，并将它们交给已经部署的微信公众号草稿 Worker。整个流程不需要人工触发，只创建未发表草稿，不具备自动发表、群发或置顶能力。

## Background

- 周期策略已经由 `WeeklyEditionSchedule` 固定为周一 09:00、`Asia/Shanghai`、24 小时补偿窗口。
- 生产服务器目前只运行微信公众号草稿 Worker；周任务调度器和周 DAG Worker 均未运行，也不存在主机 Cron/Systemd 定时器。
- 现有 `official_account_weekly_dag_main.py` 只绑定 `LocalWeeklyDagFixtureHandlers`。它是开发演示路径，不能作为真实生产内容来源；草稿适配器也会拒绝缺少真实采集凭据的 fixture 周包。
- 生产数据库已有真实采集、治理、选题、文案、图片、正式企业微信投递和公众号本地文章所需的持久化基础；周 DAG、执行治理和微信草稿审计表已迁移到 `20260901_0042`。
- 当前微信草稿适配器已在生产启用，生效最早周次为 `2026-09-07`，部署至今未创建任何草稿记录或提供方写入。

## Requirements

### R1. Production schedule

- 增加独立、默认关闭、无公开端口的生产周调度进程。
- 调度时间只能复用代码拥有的 `WeeklyEditionSchedule`：周一 09:00、上海时区、24 小时补偿；不得在 Compose、环境变量和 Python 中维护彼此可能漂移的三套时间规则。
- 进程启动或周期巡检时必须幂等对账；周一 09:00 至周二 09:00 内的重启可以补偿入队，窗口外不得补跑。
- 生产启用必须带显式确认和 ISO Monday 最早周次；任何早于 `2026-09-07` 的周次均不得创建运行、产物或微信任务。

### R2. Real weekly input

- 生产路径只能消费 PostgreSQL 中有真实采集、治理、选题和正式业务产出谱系的数据，不得使用固定 fixture、演示 JSON、静态新闻或伪造来源。
- 一周只选择三个互不重复的真实事件，按现有顺序形成 `official_anchor`、`industry_trend`、`application_case` 三个角色。
- 复用现有周选题规则、真实来源权威字段和不可变评分，不重新发明第二套打分或放宽既有事实门禁。
- 生产输入指纹必须绑定实际候选/包/版本快照。首次入队后不可因后续数据变化改写同一周的历史决策。
- 少于三个合格且相互独立的输入时，整周保持可诊断的失败或待重试状态，不得用 fixture 填充，也不得创建部分微信草稿。

### R3. Governed three-article execution

- 现有 16 节点周 DAG 的租约、fencing、重试、检查点、执行治理和三分支并发契约继续作为编排骨架。
- 增加显式的 production handler 模式；fixture handler 继续只供开发测试，生产环境必须拒绝 fixture 模式。
- 文章生成复用已配置的智谱模型和公众号本地文章生成/审计/渲染能力；确定性校验在模型审核之前执行。
- 无人工审核：只有自动质量门禁全部通过的文章才能进入周聚合；任一角色失败时不产生完整周批次。
- 周聚合必须保存可重放的三角色身份、Article/content/媒体指纹和安全产物引用，不把正文、密钥、访问令牌或私有对象路径写入运行状态和日志。

### R4. Draft handoff

- 周 DAG 只有在三篇文章全部验证成功后，才向草稿 Worker 暴露一个完整、不可变、内容寻址的三角色批次。
- 草稿入队继续使用现有一批三项、逐项副作用检查点、租约和结果未知保护；已成功角色不得重放。
- 正常结果是公众号草稿箱中三篇相互独立的未发表草稿。
- 禁止实现或调用 `freepublish`、群发、主页置顶、浏览器登录或任何自动发布接口。

### R5. Production rollout

- 生产发布必须隔离当前工作区中与本任务无关的 Reviewer、排序、IP 评测和报告改动，不得顺带部署它们。
- 发布前记录不可变代码/镜像身份，备份数据库和相关持久卷，并执行无网络的生产设置构造与候选镜像检查。
- 首次部署发生在周一 09:00 之前，只启动空闲进程并验证 `due=false`；不得手工触发 `enqueue`、不得补跑历史周、不得进行真实微信草稿烟测。
- 失败回滚必须停止新增写入者并恢复旧镜像/配置；已经发生的外部微信写入不得自动重试或假定回滚成功。

## Acceptance Criteria

- [x] 在注入时间的测试中，周一 08:59 不入队，09:00 只创建一个真实周运行；重复轮询/重启仍是同一个运行。
- [x] 周一 09:00 至周二 09:00 的停机恢复可以补偿入队；窗口结束后不会补跑。
- [x] `2026-09-07` 以前的合法周包和数据库候选均被无副作用拒绝。
- [x] 生产 handler 从真实 PostgreSQL 谱系构造三个不同角色和不同事件；fixture、重复事件、少于三项或身份漂移均在任何微信调用前失败。
- [x] 三分支自动生成使用现有智谱配置；每篇通过确定性校验和自动质量门禁，整批才可聚合。
- [x] 完整周批次只会幂等创建一个微信草稿 job 和三个 item；重复发现不会产生重复草稿。
- [x] 任一角色准备失败时微信 provider 调用数为 0；提供方写超时后状态为 `outcome_unknown` 且不自动重放。
- [x] Compose 中周 scheduler、production DAG worker、所需文章 worker 和微信草稿 worker 均无公开端口、默认关闭并有独立启用门禁。
- [x] 生产部署后所有既有业务服务保持健康、重启次数为 0，新增进程稳定运行且部署时周/Draft 审计计数仍为 0。
- [x] 第一个合格周次最终目标为三篇未发表草稿；代码和运行时不存在自动发表、群发或置顶能力。
- [x] 聚焦测试、release contract、Ruff、严格 mypy、Compose 渲染、任务校验、凭据扫描和差异检查通过；无关脏工作区保持原样。

## Out of Scope

- 自动发表、群发、主页置顶、微信网页登录和人工模拟点击。
- 补跑 `2026-09-07` 以前的历史周次。
- 修改早/中/晚三时段的新闻抓取、选题、文案或企业微信推送规则。
- 把演示 fixture 或固定新闻作为生产回退。
- 为本任务引入新的模型供应商；继续使用现有智谱生成配置和已部署的微信官方接口。
