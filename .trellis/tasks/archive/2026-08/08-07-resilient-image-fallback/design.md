# Resilient Image Fallback Design

## Problem Boundary

An accepted copy can currently be blocked permanently when a provider returns
`image_provider_rejected`, even though the package has a deterministic visual brief and approved
private assets. The application must recover without weakening provider safety policy or falsely
claiming that a catalog image was generated by the provider.

## Data Flow

```text
accepted draft + visual brief
  -> primary provider request
  -> provider rejection
  -> one neutralized provider retry
  -> success: validated provider image -> MinIO -> ready package
  -> second rejection: selected catalog asset -> square renderer -> validation -> MinIO -> ready package
```

All provider calls remain outside database transactions. Claim, stage transition, and result
persistence remain short lease-protected transactions.

## Durable State

Add `image_artifacts.provider_rejection_retry_count INTEGER NOT NULL DEFAULT 0` with a `0..1`
constraint. It is independent from the existing `repair_count`, which remains the one-time
deterministic quality repair counter. This is a migration because worker claim/recovery behavior
must remain correct across restart and concurrent workers.

`material_packages.version_snapshot.image.fallback` is the durable safe provenance record:

```json
{
  "version": "image-fallback-v1",
  "state": "not_used | neutralized_retry | brand_catalog",
  "provider_rejection_retry_count": 0,
  "initial_error_code": "image_provider_rejected",
  "asset": {
    "asset_id": "safe catalog identifier",
    "filename": "safe basename",
    "sha256": "checksum",
    "role": "action_reference",
    "selection_reason": "safe selector explanation",
    "fallback": false
  }
}
```

It excludes provider bodies, prompts, URLs, storage keys, source copy, credentials, and image
bytes. The original provider/model remain the requested-generation identity; the fallback object
is the authoritative output-source projection for UI and downloaded package metadata.

## Worker State Machine

1. A primary provider rejection increments `provider_rejection_retry_count`, keeps the package
   queued, writes `fallback.state=neutralized_retry`, and emits one warning event.
2. The next claim derives a neutralized prompt exclusively from the allowlisted visual brief and
   selected-reference descriptors. It omits the raw news title, summary, copy, and legacy prompt;
   it does not lower any provider safety rule.
3. A successful retry follows the existing output validation, optional OCR/audit, immutable MinIO
   write, and ready-package persistence path. Its fallback state remains `neutralized_retry`.
4. A second provider rejection chooses one already reserved catalog reference in stable role order
   (`action_reference`, `style_reference`, `identity_reference`). The selection is therefore tied
   to the topic's visual brief, catalog version, checksum, and original reservation.
5. The chosen PNG is decoded with Pillow, aspect-preserved and centered on a plain 1024x1024
   background, encoded as PNG, hard-validated, and written through the existing content-addressed
   MinIO store. The package becomes ready only after that succeeds.
6. The catalog fallback records `fallback.state=brand_catalog`. Its deterministic validation is
   passed only after raster validation; optional generated-text OCR and generative visual audit are
   recorded as not applicable because no model output or dynamic text was produced.
7. If catalog reading, rendering, validation, or storage fails, the artifact stays terminal with a
   typed failure. No incomplete image is delivered.

The claim budget becomes `IMAGE_MAX_ATTEMPTS + repair_count + provider_rejection_retry_count`,
so each independently bounded recovery is honored even with a configured base max of one.

## Neutralized Prompt Contract

Introduce a domain-owned prompt builder with a new version identifier. It emits only the
allowlisted visual brief fields: category, learning goal, scene, action, approved characters,
composition, and optional allowlisted visual text. It references selected inputs by ordinal and
role, never filename/path/content. It must pass the current `validate_image_prompt` bounds and is
included in the provider request fingerprint for the recovery attempt.

## API and UI Projection

`ImageArtifactResponse` gains a typed `fallback` object. It projects only the safe snapshot and
defaults to `not_used` for old rows. The frontend maps this object and displays an explicit image
source/recovery status, including catalog filename and selection reason when a catalog fallback was
used. Existing image downloads remain relative API URLs; no object locations are exposed.

## Observability

Worker events use stable names:

- `material_package_image_provider_rejected` (warning): typed error, attempt, safe IDs,
  provider/model, and next action.
- `material_package_image_fallback_ready` (info): safe IDs, recovery state, selected asset ID,
  renderer version, dimensions, and byte size.
- `material_package_image_fallback_failed` (error): safe IDs, typed fallback error, and terminal
  action.

No event contains prompts, topic/copy text, raw provider payloads, private paths, URLs, image
bytes, or secrets.

## Compatibility and Rollback

Old rows receive `provider_rejection_retry_count=0` and API `fallback.state=not_used`. The change
does not alter existing successful objects. Rollback is code-first: turn back to the prior worker
after the additive migration; new columns remain harmless, while packages that already completed
with catalog provenance remain immutable and inspectable.
