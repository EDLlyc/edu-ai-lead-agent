# 微信公众号自动推文技术路线调研与汇报

> 2026-08-19 方向调整：用户要求报告主要说明“技术怎么实现”。本次调整覆盖此前“领导版不展示项目名称”和偏业务化叙事的要求；草稿箱 + 人工发布、安全边界及不调用真实接口的约束保持不变。

## Goal

形成一份面向领导汇报、但以技术实现为主的中文 PDF。用不过度下钻源码的方式说明系统架构、数据怎样流转、微信适配如何实现、任务如何调度与恢复，以及最小闭环怎样落地。报告可点名代表性开源方案作为设计参考，但不把任何项目表述为经过验证、可直接上线的完整方案。

## Background

- 当前仓库已经具备权威来源采集、事实与事件治理、规则加 LLM 选题、品牌文案、配图、质量检查、任务状态与内部企业微信交付能力。
- 已有两份相关材料：完整行业调研和简版业务汇报。本次弱化业务背景、管理责任、泛化风险和宽泛决策内容，重点补充“系统怎样组成、数据怎样流转、接口怎样适配、失败怎样恢复”。
- 公开实现普遍把内容生产、Markdown/HTML 排版、图片上传、微信公众号草稿适配和人工确认拆成独立模块；草稿箱通常被作为自动化终点，正式发布由授权人员确认。
- 用户希望借鉴开源技术路线，但报告不出现“某开源项目可以直接拿来使用”的结论，也不展开源码级细节。

## Requirements

### R1 — 技术实现主线

- 用非研发人员也能理解的语言解释实现方案，但主要回答“怎么做”，避免函数、类、数据库表、代码片段和过细接口参数。
- 主线回答五个问题：参考了什么、整体怎样分层、文章怎样跑完整流程、微信接口怎样适配、任务失败怎样恢复。
- 报告控制在 6--8 页，业务背景、管理责任、泛化风险和宽泛决策内容只保留必要边界。

### R2 — 参考成熟实现的共性设计

- 调研微信公众号官方接口与有代表性的公开源码，重点归纳以下共性：
  - 内容生产与平台发布解耦；
  - Markdown/结构化文章转换为微信兼容的内联样式 HTML；
  - 正文图片和封面先上传，再替换为微信侧资源标识或 URL；
  - access token 缓存、固定出口 IP/白名单、失败重试和幂等记录；
  - 默认创建草稿，人工预览确认后发布；
  - 多账号、版本历史、状态追踪和数据复盘作为后续能力。
- 领导版可谨慎列出 wechatpy、Wenyan / md2wechat、wechat-publisher、auto-wx-post 等代表性方向，用一句话说明各自提供的设计启发和边界；仓库链接与许可证详情仍保留在研究记录中。
- 不复制公开项目的宣传语、界面或独有命名，不暗示其经过生产验证或能够直接替代自建系统。

### R3 — 推荐架构与流程

- 报告给出一条端到端路线：
  1. 栏目与任务配置；
  2. 可信内容采集；
  3. 事实治理与候选选题；
  4. 规则筛选后由 LLM 受控排序；
  5. 长文生成与品牌知识约束；
  6. 配图、封面与微信排版；
  7. 事实、版权、品牌和移动端预览检查；
  8. 同步到公众号草稿箱；
  9. 人工签发；
  10. 阅读与互动数据回流。
- 架构至少区分现有内容生产、文章中间稿与排版、调度/Worker/状态、微信公众号适配、人工确认与结果回流。
- 明确复用当前项目的能力与公众号方向新增能力，避免把企业微信内部交付误写为公众号发布。
- 说明 Scheduler 如何创建任务、Worker 如何领取任务、PostgreSQL 如何保存权威状态、幂等键和有限重试如何避免重复草稿，以及服务重启后如何从安全节点继续。

### R4 — 最小技术落地

- 第一步核验账号权限、草稿开关、固定出口 IP 和测试素材。
- 第二步独立完成“结构化文章 → 微信 HTML → 图片/封面 → draft/add → 状态记录”的适配器原型，不自动群发。
- 第三步接入现有采集、选题、文案和配图链路，再补 Scheduler、Worker、PostgreSQL 状态、审核入口与失败恢复。
- 多栏目、排期、数据复盘、多账号和正式发布自动化放在闭环稳定后，正式发布仍需单独审批。

### R5 — 实现约束

- 报告保留与实现直接相关的账号权限、密钥与 IP 白名单、图片合规、重复草稿、有限重试和失败恢复约束，不再展开泛化风险清单或管理责任矩阵。
- 第一阶段默认只创建草稿；最终发布由公众号管理员或授权运营人员确认。
- 不承诺公众号账号一定具备草稿、发布或群发接口权限，实施前必须以实际后台权限为准。

### R6 — LaTeX/PDF 交付

- 新建独立文件，不覆盖 8 月 17 日完整调研或 8 月 18 日简版汇报：
  - `reports/wechat-official-account-auto-publishing-roadmap-2026-08-19.tex`
  - `reports/wechat-official-account-auto-publishing-roadmap-2026-08-19.pdf`
- 使用 A4 中文排版、统一配色、页眉页脚、架构图、时序/流程图和少量表格；图表全部离线可编译。
- 不包含真实公众号账号、密钥、服务器地址、私人路径或内部业务数据。

## Acceptance Criteria

- [ ] PDF 在 6--8 页内，封面直接给出一句话技术架构。
- [ ] 正文主要说明技术实现，业务背景、管理责任、泛化风险和宽泛决策内容显著弱化。
- [ ] 至少包含开源方案参考表、整体技术架构图、端到端处理时序、微信适配实现图和调度/状态恢复图。
- [ ] 说明 Scheduler、Worker、PostgreSQL 权威状态、幂等、有限重试和重启恢复，但不展示代码、表结构或函数级细节。
- [ ] 报告明确“自动生成到草稿箱、人工确认发布”的第一阶段边界。
- [ ] 正文可出现代表性开源方案名称，但不出现 GitHub 链接、复制代码建议或“直接安装即可上线”等表述，并明确仅作设计参考、未验证直接上线。
- [ ] 任务研究记录包含微信公众号官方接口与至少 4 个代表性公开实现的链接、观察和适用边界。
- [ ] LaTeX 无错误编译；PDF 字体嵌入、中文、图表、页码和超链接显示正常。
- [ ] `pdftotext` 检查可读，构建日志无未定义引用、缺字和明显溢出。
- [ ] TeX/PDF 敏感信息扫描通过，且昨日两份报告保持不变。
- [ ] 本任务不访问公众号账号、不调用微信接口、不创建草稿、不发送文章、不部署服务。

## Out of Scope

- 开发或部署公众号自动发布系统。
- 申请公众号权限、配置 AppID/AppSecret 或测试真实草稿接口。
- 无人审核群发、浏览器模拟登录或绕过公众号权限。
- 采购选型、正式成本报价、合同或排期承诺。
- 修改现有业务服务、服务器配置或企业微信流程。

## Key Decisions

- 交付物是“技术实现路线汇报”，不是行业产品对比、业务立项或管理责任报告。
- 公开源码用于归纳架构思路，领导版可点名四类代表性方案，但不宣称可以直接复用或上线。
- 推荐路线为“复用现有内容生产能力 + 新增公众号适配与审核层”，而不是重新建设整套采编系统。
- 第一阶段终点固定为公众号草稿箱；人工负责预览、修改和最终发布。
- 报告重点讲清架构、流程、接口适配、调度状态与失败恢复，但不进入源码、数据库表或过细参数。

## Risks and Deferred Items

- 微信接口权限与规则可能变化，报告只说明设计边界；真实实施前必须在目标公众号后台重新核验。
- 开源实现质量差异较大，本任务只提炼共同机制，不对项目稳定性、安全性或生产适用性背书。
- 正式发布自动化、多账号和阅读数据接口放到后续评估，不影响本次技术路线结论。
