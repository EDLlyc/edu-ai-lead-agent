# 每日三时段独立多新闻内容生产

## Goal

将现有“每日一个选题、一个素材包、一次正式投递”的模式升级为每天早、中、晚三个独立时段。每个时段按质量选择 0--3 则新闻，目标为 2--3 则，并为每则新闻分别生成、验证、存储和投递一套独立文案与独立图片素材包。

## User Value

- 提高科学教育、AI 教育及相关前沿科技新闻的日覆盖量和时效性。
- 每条新闻保持完整表达、独立来源和独立品牌视觉，不被压缩成合集摘要。
- 形成有区别的“科教晨报”“午间观察”“晚间精选”，同时保持教育部重要内容的全局最高优先级。
- 数量增加不能降低事实、选题、文案、图片和投递安全质量。

## Background

- [`content_scheduler_main.py`](../../../backend/app/content_scheduler_main.py) 当前只有一个每日内容主时点，并持续对账同一业务日期。
- [`daily_topic_selections`](../../../backend/app/infrastructure/db/models.py) 当前锁定单个 `selected_event_id`，现行唯一键也是“业务日期 + 时区 + profile”，不能表达一个时段内的多个独立选题。
- 现有文案、图片和素材包已经按选题/运行 ID 独立版本化，可复用为每个新选题各建一套下游运行。
- 企业微信当前为每个素材包先发送正文、再发送图片，并分别持久化子结果；单 worker 会连续领取任务，但没有跨素材包的持久化节流。
- 当前自动投递有“当天已有任一 formal job 就不再投递”的日期级保护；多新闻实现必须升级为时段/素材包级幂等，不能直接删除安全保护。
- 当前 `GET /daily-topics/{business_date}` 与前端预览是单日 Top 1 契约。新时段集合需要新增 API 视图，旧响应继续服务历史回放。
- 现有抓取每天 06:30 运行一次，若不增加时段化抓取，午间和晚间无法纳入当天新发布的新闻。

## Requirements

### R1. 三个独立时段与时间窗口

- 定义稳定业务键 `morning`、`noon`、`evening`，展示名分别为“科教晨报”“午间观察”“晚间精选”。
- 默认目标投递时间为 07:30、12:30、18:30，均使用 `Asia/Shanghai`。
- 时间点表示开始投递目标，不表示开始生成。上游应提前 60--90 分钟抓取、治理、选题并生成素材。
- 素材提前完成不得提前发送；目标时间到达后，已完成素材按排名发送，未完成素材可在目标时间后 60 分钟内补发。
- 超过 60 分钟窗口仍未具备投递资格的素材记录明确的错过窗口结果，不得自动挪到下一个栏目或次日补发。
- 三个栏目分别具有独立启用开关、目标时间和安全有界配置；功能默认不得改变现有生产单日流程。

### R2. 时段化增量抓取与确定性候选边界

- 每个启用时段拥有独立、幂等的 scheduled acquisition run；现有来源游标、请求节流、SSRF/DNS/HTTPS/路径/响应限制保持不变。
- 时段选题只能在对应抓取与治理达到允许的终态后开始，并持久化确切的 acquisition/governance lineage 与 governed cutoff。
- 候选集包含 cutoff 前已治理且仍在新鲜窗口内的合格事件，使早间未入选的高质量新闻可参与后续时段；该日已经选中的事件必须排除。
- 并发、重启、catch-up 或手工回放必须收敛到同一时段运行，不得创建重复来源请求或使用尚未完成的治理结果。

### R3. 每时段 0--3 个独立选题

- 每个时段最多选择 3 则，目标选择 2--3 则；合格候选不足时允许选择 1 则或 0 则。
- 不得为凑够数量降低阈值、创造资格、忽略来源/证据要求或覆盖任何硬性否决。
- 每个选中事件拥有稳定时段内序号、独立选题记录和完整分数/原因投影；未填满的位置要记录可解释原因。
- 同一时段不得重复事件，同一天跨时段不得再次选择相同或实质相同事件；治理事件聚类与历史七日重复规则继续生效。
- 选择必须确定：相同不可变候选集、配置、cutoff、时段和已选集合产生相同顺序与结果。

### R4. 既有资格和最高优先级不变

- 继续使用现行 `.6` 资格、阈值、veto 和教育部来源认证边界，不重解释 `.4`/`.5`/`.6` 历史结果。
- 教育部发布的 AI 教育、科学教育重要新闻在任一后续时段保持最高优先，不因栏目偏好被推迟。
- 产品适配只能提高既有合格候选的排序，不能使范围外、融资、普通消费科技、一般算力或其他硬否决内容获得资格。
- 新增版本化栏目软偏好只影响已确定资格后的排列：
  - `morning` 偏好教育部政策、科学教育、AI 教育与国际权威动态；
  - `noon` 偏好学校实践、课程应用、科技教育、白名单赛事、科技特长生、强基计划与综评；
  - `evening` 偏好当日重点、机器人和前沿科技突破，以及与产品矩阵自然相关的内容。
- 栏目不设题材硬配额；偏好候选不足时回退到整体合格排名，仍不足则少选或不选。

### R5. 每则新闻独立生产

- 每个选中事件独立创建文案运行、图片产物和素材包；一则失败不能回滚或阻塞同批其他内容单元。
- 每则使用完整朋友圈文案口径，目标为 180--240 个汉字，不使用合集的 80--120 字摘要格式。
- 每则保留独立证据、来源名称、原文链接、事实绑定、品牌绑定、审计与版本信息。
- 每则独立生成一张内容匹配、使用已批准赛先生/小赛 IP 资产的图片；不得复用同一图片冒充不同新闻结果。
- 现有文案修复上限、图片验证/审计、提供商失败兜底、MinIO 私有存储和幂等指纹继续生效。

### R6. 自动顺序投递与持久化节流

- 通过现有质量门的独立素材包自动投递，无需逐条人工点击；人工审核配置仍是可保留的总开关。
- 同一时段默认按选题序号投递；当前未就绪、已失败或未知的素材不得阻塞其他已就绪素材，任何时刻均以已就绪集合中的最小序号优先。每套素材内部仍先正文、后图片，并在发送第二个子消息前持久化第一个结果。
- 相邻素材包的实际投递开始时间默认至少间隔 60 秒；该规则必须使用数据库持久化状态，在多 dispatcher、重启和回放下仍成立，不能只依赖进程内 `sleep`。
- 每套素材拥有独立请求指纹、尝试、文本/图片子状态和终态。已成功子消息不得重发，`delivery_unknown` 不得自动重试。
- 某一素材包失败或未知只影响该素材包；其他素材包按自身持久化状态与节流规则继续处理。
- 旧单日素材包继续使用原日期级 formal 防重；新时段素材包使用时段/素材包级唯一性，不能让历史包被部署或轮询重新发送。

### R7. 历史兼容、API 与审核台

- 历史每日 Top 1、旧 acquisition run、`.4`/`.5`/`.6` 分数、旧文案/图片/素材包/投递必须继续精确查询与回放，不重写历史行。
- 新增按业务日期查询三个栏目、每个栏目 0--3 个选题及下游状态的 API；现有 daily Top 1 API 保持原响应和历史语义。
- 素材包列表/详情增加安全的栏目、序号和目标窗口投影，不暴露私有路径、提示词、对象键或凭据。
- 前端审核台按日期和栏目展示独立素材包、少选/空栏目原因、质量状态和投递状态；仍不提供公开社交平台自动发布控件。
- OpenAPI 是唯一前后端 wire contract，生成类型不得手工修改或绕过。

### R8. 分阶段放量与可观测性

- 三个栏目能力一次开发并完成离线、数据库和跨层验收，但生产配置逐步启用。
- 第一阶段仅启用晨报；连续完成 2 个无重复、无误发、无未知投递的合格时段后才能启用午间。
- 第二阶段完成 2 个合格的晨报+午间时段并验证跨时段去重后，才能启用晚间。
- 任一阶段出现重复、异常刷屏或未知投递，不启用下一档；已验证栏目可继续运行。
- 日志和安全投影记录日期、栏目、run/item/package ID、序号、版本、选择/未选择原因、目标/实际时间和安全错误码，不记录正文、图片、私有 URL 或凭据。

## Acceptance Criteria

- [ ] 三个时段使用稳定业务键和时区，可独立调度、补偿、停用、重试和回放。
- [ ] 每个时段在受控候选集上确定性选出 0--3 个互不重复事件，并持久化所有排名、软偏好与少选原因。
- [ ] 栏目软偏好不能改变资格、覆盖 veto、提高阈值状态或推迟尚未发布的教育部最高优先新闻。
- [ ] 同一天最多形成 9 套独立素材包；并发或重放不会突破上限或产生重复事件。
- [ ] 每套素材包均可追溯到时段/序号、独立选题、证据、完整文案、独立图片和不可变版本。
- [ ] 单条文案/图片失败只影响其自身；其他同批内容仍进入各自正确终态。
- [ ] 目标时间前不发送；目标时间后 60 分钟外不自动发送；晚完成内容不会跨栏目或跨日补发。
- [ ] 相邻素材包实际开始投递至少相隔配置的 60 秒，多 dispatcher、重启或重放不能绕过节流。
- [ ] 每套素材的正文/图片子结果持久化，成功子消息不重发，未知结果不自动重试。
- [ ] 老的单日 Top 1 API 和历史 `.4`/`.5`/`.6`、文案、图片、投递回放保持兼容。
- [ ] 新 API 和前端可以检查三栏目、每条独立素材、空位原因、质量和投递状态。
- [ ] 新迁移可从当前唯一 head `20260807_0019` 升级，真实 PostgreSQL 约束、升级/降级测试通过，现有数据保持不变。
- [ ] 后端 format/lint/strict mypy/全量测试、前端 contract/format/lint/typecheck/test/build、Compose、doctor 与 `git diff --check` 全部通过。

## Out of Scope

- 将多则新闻融合为一条合集文案或一张拼图。
- 自动发布到朋友圈或其他公开社交平台。
- 训练新的评分模型，降低抓取安全、证据、图片、隐私或企业微信防重策略。
- 在本任务中修复 CAST/EdSurge、处理云效/ACR 发布流水线或部署到真实生产服务器。
- 根据点击、转化或用户行为自动调权；该闭环在稳定采集运营数据后另行规划。

## Risks and Deferred Items

- 每日最多 9 次文案和图片生成会提高模型调用量、耗时与成本；现有预算、并发、lease/heartbeat 和提供商兜底必须继续限制风险。
- 上游准备提前会牺牲目标时间前最后一小时的新鲜度；午间、晚间通过各自增量抓取补充当天新内容。
- 分阶段生产启用和真实企业微信验收属于后续发布任务；本任务只提供默认关闭的能力、配置、证据与运行手册。
- 两个 pending 信源保持独立后续任务，不得借多时段上线绕过 live parser gate。
