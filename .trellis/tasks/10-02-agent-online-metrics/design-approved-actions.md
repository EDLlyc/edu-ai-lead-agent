# 方案：诊断后经批准自动执行（草案，待负责人决定）

## 目标

告警诊断 Agent 给出“重新发送”“重跑文案”这类建议后，运营一次批准，系统执行并自动核对结果；
Agent 本身始终拿不到写权限，每一步都留痕，可以随时一键关掉。

## 现状（2026-10-02）

- 诊断 Agent 只读（`edu_ai_ops_ro`），建议只写进告警和日志；告警目前只写日志（缺内部群 webhook key）。
- 已有可复用的执行入口：
  - 重新发送：`POST /api/v1/wecom-deliveries/{id}/retry`（`retry_wecom_delivery` 自带状态和截止校验）；
  - 重试配图：`POST /api/v1/material-packages/{id}/image/retry`；
  - 需人工检查的稿件：已有人工加推的审核/修改/推送页面。
- 没有“重跑文案”的入口，需要新做。

## 设计

1. **只开放窄动作，不给通用写权限**。第一批只做 `retry_delivery`（复用现有接口），第二批再评估
   `rerun_copy`（新接口，会产生模型调用成本）。动作是白名单，参数只有目标 id。
2. **建议 → 批准 → 执行 → 核对** 四步分离：
   - 诊断 Agent 产出结构化“动作提案”：动作、目标 id、理由、依据的任务、失效时间，存进新表
     `ops_action_proposals`（需要一次数据库迁移）。
   - 运营批准：先用本地运维助手页面（已有 interrupt 审批卡片）和命令行 `ops approve <id>`；
     企业微信里的审批链接需要公网可达的审批页和身份校验，安全成本高，暂不做。
   - 执行：由服务器上的应用（不是 Agent）用应用自己的权限调用现有接口；执行前**重新校验前置条件**
     （状态没变、没过截止、同一目标没执行过），不信任提案里的判断。
   - 核对：执行后一段时间（例如 10 分钟）由诊断 Agent 再查一次，结果写回提案并记日志。
3. **护栏**：
   - 每条提案只能执行一次（幂等键），过期作废（时段目标时间 + `CONTENT_SLOT_DELIVERY_LATE_MINUTES`，现为 60 分钟）；
   - 频率上限：每天每类动作不超过 3 次，同一目标最多 1 次；
   - 审批人、审批时间、执行结果、核对结果全量留痕；
   - 总开关 `OPS_ACTIONS_ENABLED`（默认关），关掉后只产出提案不执行；
   - Agent 侧仍只有只读账号，写操作只在执行端发生。
4. **评测与灰度**：
   - 合成故障上评测“该不该提案、提案对不对”（沿用 evals/ops_diagnosis，加上提案正确率）；
   - 执行端单测：状态已变、已过期、重复批准、非白名单动作、频率超限都必须拒绝；
   - 先开“只提案不执行”一周，看提案质量，再打开执行。

## 工作量与上线

约 1.5–2 天：迁移 1 张表、提案生成、执行端（先 1 个动作）、命令行与运维助手页面接入、核对、测试。
上线涉及数据库迁移和服务镜像更新，按惯例在时段外、无任务运行时进行，需要负责人确认。

## 需要负责人决定

1. 审批渠道：建议先用运维助手页面 + 命令行，企业微信审批链接暂不做。
2. 第一批是否只做“重新发送”，“重跑文案”放第二批。
3. 补发截止：沿用时段目标时间后 60 分钟，还是更短。
4. 是否先“只提案不执行”一周。
