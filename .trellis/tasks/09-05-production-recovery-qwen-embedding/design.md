## Boundaries

Keep the deployed independent acquisition/governance/content/dispatcher processes, PostgreSQL
durable job authority and immutable private MinIO artifacts. Do not treat a model response or
API enqueue as proof of delivery. Inspect settings at each actual consumer; content-worker
does not own WeCom credentials. First recovery release retains all current model providers.

## Recovery flow

1. Refresh full release/digest identities, service health, date/windows and protected history.
2. Audit/build a bounded no-send diagnostic against the deployed version: provider/client
   construction, active-brand lookup, copy input bounds and output validation. Freeze call
   limits and isolation before live requests. A no-send check cannot create an auto-deliverable
   package or leak private text. Do not invent new accounts or infer credentials.
3. Correct only evidenced blockers with small tested patches.
4. Observe the next legitimate slot through accepted copy, validated material package and the
   normal formal dispatcher job. Do not reopen terminal runs, fabricate topics, reset SQL job
   state, extend windows or force a new version just to trigger delivery.
5. Verify terminal delivered plus no duplicate after another scheduler/dispatcher pass. Any
   failure remains an explicit unfinished acceptance criterion.

## Rollout and rollback

Use a clean task-only release projection, preserving dirty main. Reuse the tested digest/source
release mechanism without a generic tooling rewrite. Before mutation, capture the required fresh
backup and old image/source/config identities; fence the protected history. Quiesce only necessary
consumers if a change requires it. Verify migration head, owned provider clients and image/config
convergence after activation. Rollback must restore code and scoped configuration coherently,
not overwrite valid new events with an old full database or erase sends.

### Narrowly bound release transaction

The ordinary deployer requires a different protected-file ownership/manifest state and does not
own primary-environment rollback. The archived hotfix transaction is deliberately pinned to its
older incident and must not be edited or executed unchanged. A new task-local derivative under
`research/substantive-release/` may reuse its proven transaction for this exact deployed base and
the reviewed candidate allowlist; it is not a generic release-framework rewrite.

- Bind exact current base/image/environment identities, a fresh complete source baseline,
  fetched candidate authority and immutable source/OCI manifests. Reject unreviewed application
  paths, unchanged-current or mismatched candidate identities, and stale time/baseline captures.
- Change only the existing unambiguous `CONTENT_SCORING_VERSION` assignment from .11 to .12.
  Duplicate/missing/unexpected values fail closed. Preserve other bytes and exact mode/UID/GID.
  Never print protected contents. Environment fingerprint checks distinguish old and new stages.
- Preserve lock, preflight, candidate image/source parity, pre-quiescence and post-backup fences,
  one-shot attempt identity, fresh backup, exact frozen-history/counter assertions and all
  application services. Finish before the next natural preparation; do not extend/suppress
  schedules or reset queues to accommodate deployment.
- Rollback restores exact old source/image/configuration together and verifies protected
  history after restart. No wholesale database rollback or deletion of legitimate sends.
- An unchanged Alembic head is not sufficient once genuine .12/v4 durable runs exist. Immediate
  rollback is authorized only under a zero-new-.12-work fence; finish at least 15 minutes before
  the earliest actual producer/preparation cutoff. Later rollback requires explicit stored-
  snapshot compatibility review, never deletion/relabeling of new runs.
- Require independent executable regression checks for one-key mutation, drift at each boundary,
  atomic installation failure, environment identity restoration and inherited release invariants.
