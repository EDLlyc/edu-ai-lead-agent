# Sep 16: replace images in the existing draft only

This is the later explicit user authorization to generate five article-specific
images and update the **same already-created draft**, not the earlier catalog-only
delivery and not recovery of the original unknown generation. No SQL mutation,
second draft, publication or mass-send is authorized here.

## Runtime split

- `generated-draft-update.py`: run in the existing **local-worker** runtime that
  already has the Comfly generator and Zhipu auditor configured. Mount the real
  protected draft journal and catalog read-only where possible (journal requires
  writes in generation mode). No WeChat credentials are required for generation.
- `draft-generated-update-only.py`: run in the existing **draft-worker** runtime,
  which has the correct WeChat AppID and secret. Mount the same journal and catalog.
  No image model settings, keys or calls are needed in this stage.
- Keep the affected single-draft consumer stopped throughout. Do not change its
  permanent configuration or copy secrets across runtimes.
- All three operator files must be adjacent; `manual-draft-now.py` is immutable.
  The update operator verifies the reviewed generation script hash; the generation
  operator verifies the original manual script hash. Verify deployment bundle
  checksums before execution. Use the independently checked versions only.

## Commands inside the appropriate runtime

```sh
PYTHONPATH=/app python /operator/generated-draft-update.py
PYTHONPATH=/app python /operator/generated-draft-update.py --generate
PYTHONPATH=/app python /operator/draft-generated-update-only.py
PYTHONPATH=/app python /operator/draft-generated-update-only.py --update
```

Both defaults are local, read-only plans: no models, uploads or WeChat requests.
The update plan requires all five generated body images and six passing audits
to exist already. The first `--generate` freezes a two-hour authorization window,
bounded by the same Shanghai calendar day. Resuming never refreshes it.

Generation executes five distinct paid physical requests and audits the final
upload bytes of every body image plus the actual cropped cover. Each operation
persists its intent before dispatch and its result afterward in the protected
account journal. Completed records are reusable; **an intent without a matching
result is unknown and cannot be replayed**. Do not delete such a record, change its
identity or restart under another prefix.

Update rechecks the original SQL identities and add ACK, audits and byte checksums;
reads only the exact draft bound to that ACK; and refuses to overwrite changed
title, author, summary, text, links, images or cover. It reuses the original two
banner upload ACKs, uploads five replacement images and the audited cover, and
issues one journaled `draft/update` for article index zero. Source links stay
cleared. Unknown upload/update outcomes stop; they are not automatically retried.
Successful update replays return the existing local ACK without another write.

Only safe fingerprints/counts appear on stdout. The original media ID, image URLs,
generated bytes and transport receipts remain in the protected journal. An API
success ACK is reported honestly as acknowledged, not as a post-update readback
verification or publication. Original unknown generation rows and historical
catalog-delivery receipts are never rewritten.

## Explicit terminal-invalid replacement

The first production generation under script `98b643…` exited with the safe code
`image_output_invalid`. No image result or audit was persisted. This observation
does not identify the underlying format problem and does not prove the provider
never accepted or charged for that request. The original intent stays immutable.

The separately approved replacement binds the exact original image-zero intent,
original script checksum and observed error to one attempt-two authorization. It
uses a different physical provider key and separate intent/result records. It
cannot refresh the generation deadline or authorize a third attempt.

```sh
PYTHONPATH=/app python /operator/generated-draft-update.py \
  --recover-terminal-invalid 0 \
  --observed-intent-fingerprint fc6a1e15fec14f375e99056f22320e4abcbc2b0e5c5a8f3cf186060c7c8ef57f
PYTHONPATH=/app python /operator/generated-draft-update.py --generate \
  --recover-terminal-invalid 0 \
  --observed-intent-fingerprint fc6a1e15fec14f375e99056f22320e4abcbc2b0e5c5a8f3cf186060c7c8ef57f
```

The compatibility adapter retains the existing provider URL, public-address,
response-size and single-POST boundaries. Only a decodable, bounded, single-frame
JPEG/PNG/WEBP is eligible for EXIF orientation correction, RGB conversion and
deterministic fitting to 1536×1024. The journal labels this transformation explicitly
and stores source/output checksums and dimensions; it does not claim native size.
All final upload bytes still require the existing six strict quality audits.
Timeouts, network failures and crashes remain unknown and never gain terminal
replacement authority merely because their result record is absent.

## Later reconciliation: original draft no longer available

The attempted update stopped before any upload/update intent: exact `draft/get`
returned HTTP 200 with error 40007. A separate bounded inventory check found six
drafts, no original ACK media ID and no matching title/author. The cause of the
original draft's disappearance is unknown; its historical ACK remains unchanged.

`draft-generated-final-add.py` is a separate, reviewed completion operator. Its
default **read-only network plan** (unlike the earlier local-only plans) checks
exact-target 40007 plus the complete six-item inventory, including all article
subitems. Only safe counts and a snapshot fingerprint are returned or retained.
An old target or matching title/author anywhere in the inventory blocks creation.

```sh
PYTHONPATH=/app python /operator/draft-generated-final-add.py
PYTHONPATH=/app python /operator/draft-generated-final-add.py --apply \
  --inventory-fingerprint <safe-fingerprint-returned-by-plan>
```

Apply freezes a separate same-day authorization and rechecks exact absence before
uploading and immediately before one `draft/add`. It reuses all five generated
images, six audit receipts, article text and existing banner URLs; it calls no
models. Each new upload and the add have distinct durable intent/result records.
The original ACK, failed-update history and generation history are preserved.
Unknown new add outcomes never permit another add, even if the old target is
still absent. Successful repeats reuse the new ACK. There is no publication.
