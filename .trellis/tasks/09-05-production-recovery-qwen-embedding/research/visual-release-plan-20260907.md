## 3. 修复前发现的部署阻碍

独立研究见 [发布审查](visual-release-readiness-review-20260907.md)。

修复前 Compose 没有把 `OFFICIAL_ACCOUNT_LOCAL_VISUAL_PIPELINE_VERSION`、
`IMAGE_QUALITY_AUDIT_MODEL` 传入服务。现有共享环境却将
`OFFICIAL_ACCOUNT_LOCAL_GENERATED_VISUALS_ENABLED` 传给各 Python 服务。
全局开启生图而没有新策略时，配置校验会走旧版“只允许一次尝试”的分支；
补上策略参数仍不能解决问题，因为当前 Settings 把策略选择与生图执行能力绑定，
使有意不持有生图权限的 scheduler、draft 等角色也被要求配置模型。

使用实际全 profile Compose 渲染及合成配置进行离线复现：

| 场景 | 13 个应用角色的 Settings 结果 |
| --- | --- |
| 现有 generated=false | 13 通过 |
| 按当前 Compose 打开新链路 | 13 失败 |
| 仅在内存补齐缺失 marker | 3 通过、10 失败 |

这些是纯配置实例化诊断，不是启动 13 个容器，不涉及真实模型请求。
共享开关的能力耦合在旧代码已存在，但本次严格链路激活前必须修复；
已有 81 项运行时专项测试没有覆盖这一完整部署边界，不能代替启动回归。

## 4. 已批准的有界修复（本地实现及检查完成）

用户确认：“好的，请你处理，也不需要这么严格，能跑起来就行。”
本轮只修真实启动阻碍和验证排队行为，不扩展历史问题整改或发布框架重写。

1. 将不可变策略身份与执行模型的能力分开。API、weekly scheduler/DAG 与实际
   Article worker 必须对同一新任务形成一致身份；选择/等待任务不应因此持有模型密钥。
2. 按服务职责传递严格策略；只有实际生图执行者开启生成能力。草稿消费者按持久化
   v2 证据验证上传，不因全局策略被赋予生图能力。保留现有文字/图片密钥隔离，
   不给所有服务分发模型密钥，不修改一般 image_max_attempts=3 来绕过旧校验。
3. 补全实际渲染 Compose 的所有应用角色 Settings 启动测试：关闭/开启、缺 key、
   错路由、历史身份兼容、同一策略身份、无新增凭据传播。必须覆盖工具迁移角色，
   不能只测 Article worker 的手工配置。
4. 补一个无付费调用的完整三角色时间线回归：现有 3 个 weekly 节点并发等待，
   而实际 Article worker 只有 1 个，720 秒等待包含排队时间。验证节点超时后
   Article 继续完成、重试复用同一身份、根预算不足显式失败；不借测试提高并发/超时。
5. 独立检查上述最小修复，再形成新提交候选。此时才重新制定镜像/迁移发布清单，
   不把当前提交或这份提案标记为可直接部署。

这个提案不包含生产重启、推送远端、数据库迁移、旧任务重跑或付费模型调用。
